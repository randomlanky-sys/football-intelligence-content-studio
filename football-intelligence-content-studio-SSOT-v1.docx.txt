Product definition 3.1 Positioning For independent football content creators who turn match footage into tactical breakdown videos, the Studio is a local-first browser workspace that links every on-screen claim to evidence and exports a finished, narrated, annotated video. Unlike general video editors (no football semantics, no evidence) and professional analysis suites (built for clubs, heavy on tagging, light on publishing), it optimises the path from evidence to a publishable, defensible breakdown. Differentiation is a hypothesis until FG-4 interviews confirm that creators lose most time on evidence-to-video assembly and on defending claims. Established analysis products already cover tagging, data and sharing, so those capabilities alone are not a moat. 3.2 Personas and jobs-to-be-done Persona Job to be done Success looks like Phase Independent creator (primary) Turn a match clip + notes into a credible tactical video fast Reviewed, playable export in a single session; no lost work P0 Coach / analyst (secondary) Annotate sequences and present to players Reusable templates, accurate overlays, offline-capable P0 shared core, P1 specifics Reviewer (future) Check claims and comment Read-only access, no download rights unless granted P1 Support operator Diagnose without seeing private content Metadata-only tooling, audited exceptions E Platform admin Run the service safely Audited actions, no default content access E 3.3 Principles (binding) Evidence before interpretation: every claim links to footage, data or a human observation. Human authority: AI output is a proposal; approval binds to a specific evidence version. No silent damage: never silently drop edits, switch identities, shift timing, overwrite newer data or report failed export as success. One project truth: video, data, tracking, annotations, narration, evidence and exports share one versioned model. Uncertainty is visible in UI and data (confidence, calibration state, sync state). Local-first means user-controlled processing, not a promise that browsers keep large media forever. Benchmark first: no performance, tracking or AI-quality claim without measurement. 3.4 Non-goals (P0) Automated multi-player tracking at scale; autonomous tactical conclusions; match predictions. Live/streaming analysis; mobile native apps; collaboration; marketplace; provider data licensing. Mandatory accounts for local work; silent cloud upload; training on customer footage. Guaranteeing every codec, device, match length or footage condition. 3.5 Reconciliation with the original brief The first brief described a stats-and-events analytics platform; the later decisions pivoted to a tactical breakdown studio. Architecture 6.1 Principles Modular monolith first. One web app plus packages; services appear only when a measured need exists (phase E). Functional core, imperative shell. Timebase, geometry, metrics, validation, evidence hashing are pure, deterministic and heavily tested; I/O lives at the edges. Ports and adapters. Storage, AI, rendering, billing and auth sit behind typed ports; providers are replaceable but not assumed interchangeable. Schema first. Zod schemas generate JSON Schema, TypeScript types, OpenAPI and the project-file spec from one source. Command log + snapshots. All edits are commands; undo/redo, autosave, sync and audit derive from the same log. Workers for everything heavy. Demux, decode, hashing, parsing, overlay rendering, encoding run off the main thread. Degrade gracefully. Floating-point seconds are never stored or used as identity. Source media: each asset stores timescale (integer) and a per-frame table of pts and dts (typed array blob, VFR-safe) plus frame_index to pts mapping. Frame stepping uses the table, never +1/fps . Rounding: converting project time to a frame uses the greatest frame whose pts &lt;= t (floor) for display and round-half-even for export frame selection. One rule, tested by property tests. Match clock to media: clock_mappings per period: anchor list of {match_clock_ms, source_pts} with at least two anchors; piecewise-linear interpolation; stored residual_us per segment. Residual above [PB-06] marks Sync Needs Review. Output time: derived from the scene graph on render; conversion tested for drift after trim, reorder, narration shift, and preset change. Missing timestamps: imported events without time are stored but flagged unaligned and excluded from time-based metrics. 7.2 Pitch coordinates and calibration (closes REV-006) Units: metres. Default pitch 105 x 68, configurable per match. Origin: bottom-left corner when the home team attacks left to right in period 1. x along length, y along width. attack_dir ( ltr or rtl ) stored per team and period; imported coordinates are transformed to canonical form and the raw values kept. Calibration: 3x3 homography H per camera-shot segment ( t_start_us , t_end_us ) with state none , calibrated , uncertain , stale . A camera cut or zoom beyond tolerance marks the segment stale . Pitch-anchored annotations require calibrated ; otherwise the editor offers frame-anchored mode and explains drift risk. Reprojection error (px) is stored with each calibration and displayed; no accuracy claim is made beyond measured error. 7.3 Project file and versioning Portable file .studio = ZIP: project.json (schema studio.project/1 ), media.manifest.json (fingerprints, no bytes), ops.ndjson , evidence.json , README.txt . Every file carries schema_version . Migrations are forward-only functions with golden-file tests; unknown future versions open read-only with a clear message.
